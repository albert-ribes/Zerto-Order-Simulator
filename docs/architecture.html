⚡ Order Simulator App

Simulador d'ordres de productes en temps real · HPE Tech Experience Center (TEC) · Barcelona

nginx · HTML5 · JS · Chart.js FastAPI · Python 3.12 · Gunicorn PostgreSQL 16 · SQLAlchemy 📡 Observability Console

Order Simulator App és una aplicació full-stack que genera ordres de venda aleatòries entre clients i productes, les emmagatzema a PostgreSQL, i les visualitza amb gràfiques interactives en temps real.

A més de l'aplicació principal, inclou una Consola d'Observabilitat independent que monitora l'estat de tots els serveis de la infraestructura i integra les dades de protecció Zerto via API.

🖥 Frontend

SPA en JavaScript pur sense frameworks. Inclou selector de rang temporal estil Grafana, suport multiidioma (CA/ES/EN) i tema clar/fosc.

⚙️ Backend

API REST amb 40+ endpoints. Inclou generador automàtic d'ordres amb model probabilístic de franja horària (Poisson).

3 microserveis independents (db-probe, sys-probe, zerto-probe) monitorats des d'un dashboard central amb refresh automàtic cada 5 s.

API · Autenticació

Autenticació basada en JWT (HS256) via Bearer token. El token s'obté amb POST /auth/login i s'ha d'incloure a la capçalera Authorization: Bearer <token> en totes les peticions protegides.

Auth endpoints
POST /auth/login Login amb usuari/contrasenya (form-encoded). Retorna token JWT + info usuari. públic
GET /auth/me Informació de l'usuari autenticat. auth
GET /auth/users Llista tots els usuaris del sistema. admin
POST /auth/users Crea un nou usuari. Body: { username, password, is_admin? } admin
PUT /auth/users/{id} Actualitza password i/o rol d'un usuari. admin
DELETE /auth/users/{id} Elimina un usuari. No pot eliminar el propi compte. admin 
# Exemple login
curl -X POST http://backend.tec.bcn:8000/auth/login \
  -d "username=admin&password=admin"

# Resposta
{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "bearer",
  "username": "admin",
  "is_admin": true
}

API · Generador automàtic

El generador executa un thread Python que crea ordres aleatòries seguint un model de Poisson modulat per franja horària. Entre les 22h i les 6h no genera ordres. El pic de generació és al voltant de les 10h i 15h.

Generator endpoints
POST /generator/start Inicia el generador. Body opcional: { interval: 2.0 } (segons entre cicles). Mínim 0.5s. auth
POST /generator/stop Atura el generador. L'estat es persisteix a generator_state.json. auth
GET /generator/status Retorna { running, interval }. Endpoint async — sempre respon fins i tot amb el thread pool exhaurit. públic
Model Poisson: cada cicle es genera un nombre d'ordres k ~ Poisson(λ) on λ = weight × 2.0 i weight ∈ [0.03, 1.0] en funció de la hora del dia.

API · Estadístiques

Tots els endpoints d'estadístiques accepten els paràmetres opcionals start i end en format ISO 8601 (e.g. 2026-04-01T00:00:00Z).

Stats endpoints — tots públics (no requereixen autenticació)
GET /stats/range Min/max created_at de les ordres. Usada per inicialitzar el selector de rang. públic
GET /stats/summary KPIs: total ordres, facturació, clients, productes. Inclou sèrie acumulada i darrera ordre. públic
GET /stats/timeline Sèrie temporal amb granularitat automàtica: ≤3h→minut, ≤24h→10min, ≤7d→hora, >7d→dia. Sense buits. públic
GET /stats/daily Agregats per dia natural. Tots els dies del rang estan presents (zeros si no hi ha ordres). públic
GET /stats/hourly Distribució per franja horària 0–23h. Inclou avg_count i avg_revenue per dia. públic
GET /stats/products Estadístiques per producte: quantitat venuda i facturació total al rang. públic

API · Health & Sistema

Health endpoints — tots públics i async (no bloquegen el thread pool)
GET /ping Ping bàsic sense DB. async def → respon sempre fins i tot quan la DB és pausada i el thread pool és exhaurit. públic
GET /db/ping Latència de la DB. Retorna { status, latency_ms } o 503 si la DB no respon. públic
GET /health Salut completa: backend + DB. Retorna { status, database, db_latency_ms }. públic
GET /system/metrics async def → CPU (interval=None), RAM, disc, uptime. Mesures del servidor backend. públic
Resiliència: /ping, /generator/status i /system/metrics són async def — no ocupen el thread pool de Gunicorn. Quan la DB és pausada i les queries de /stats/* pengen indefinidament exhaurint el pool, aquests endpoints continuen responent.

Model de dades

Quatre entitats principals gestionades per SQLAlchemy ORM. L'eliminació d'un client o producte elimina les seves ordres en cascada (FK amb ON DELETE CASCADE).

🧑 User

Gestió d'accés a l'aplicació. Hi ha sempre un usuari admin per defecte creat a l'arrencada si no n'hi ha cap.

Empresa compradora. L'email és únic al sistema. Té relació 1→N amb ordres.

📦 Product

Producte a la venda. El preu (NUMERIC(10,2)) es copia a l'ordre en el moment de la venda.

Venda. Inclou unit_price (snapshot del preu) i total_price calculat. FK a client i producte.

Mòduls JavaScript (Frontend)

api.js

109 líniesfetch wrapper

Centralitza totes les crides HTTP. Gestiona el token JWT (localStorage), respon als 401 fent logout automàtic i exposa l'objecte api amb mètodes per a auth, clients, productes, ordres, stats i generador.

La funció login() llança errors tipats: network_error, credentials_error, backend_error.

app.js

lògica principalauthTRP

Inicialitza l'aplicació, gestiona el login/logout, la navegació per pestanyes i el tema. Conté la Time Range Picker (TRP) Factory makeTRP(ids, onChange) que crea selectors de rang temporal independents amb presets (15m–30d) i rang personalitzat.

Detecta localhost per mostrar el badge 🐳 dev i modificar el document.title.

charts.js

Chart.js 4.4visualització

Instàncies i helpers de Chart.js. Implementa: paleta de 8 colors, coloració per franja horària (blau nit, taronja alba, ambre dinar, verd hores laborables), marcadors de dia en gràfiques multi-dia, i alineació precisa dels eixos entre gràfiques.

i18n.js

CA · ES · EN~90+ claus

Sistema de traducció. Les claus s'apliquen via atributs data-i18n al DOM. Suporta interpolació de variables amb ti(key, {n: 5}). El canvi d'idioma persisteix a localStorage.

Probes / Microserveis d'Observabilitat

💻 sys-probe

port 5001psutilThreadingHTTPServer

Exposa mètriques del sistema operatiu del servidor on s'executa. S'instal·la a frontend.tec.bcn i postgresql.tec.bcn com a servei systemd.

EndpointRetorna
GET /sys/metrics{ cpu_percent, mem_total_mb, mem_used_mb, mem_percent, disk_total_gb, disk_used_gb, disk_percent, uptime_s }

🛡️ zerto-probe

port 5002stdlib onlycache 20sdual ZVM

Agrega dades de dos Zerto Virtual Managers (ZVM) via API REST. Autentificació multi-mètode (OAuth2 client_credentials → password grant → Basic auth). Les dades es fan cache 20 s per no sobrecarregar els ZVMs. Detecta possibles atacs ransomware via sub_status, events i alertes.

Dades recollides per ZVM

  • VPG: nom, estat, sub_estat, RPO, historial, failsafe, IOPs, storage
  • VMs: nom, estat, RPO, storage, journal, IOPs
  • Alertes: nivell, descripció, entitat, estat
  • Events: descripció, hora, tipus, categoria, lloc, usuari

Variables d'entorn ZVM

ZVM1_HOST=10.20.0.152
ZVM1_CLIENT_ID=grafana-client
ZVM1_CLIENT_SECRET=...
ZVM2_HOST=10.20.0.121
ZVM_VPG_NAME=ResilienceApp
SCRAPE_SPEED=20
ThreadingHTTPServer: tots els probes usen ThreadingHTTPServer (no l'HTTPServer simple) per evitar que una petició lenta (e.g. query SQL que penja) bloquegi les peticions posteriors.

Producció

En producció, tots els serveis corren com a processos natius a VMs Ubuntu 24.04 LTS. El repositori es clona a /opt/zerto/ i s'usa un virtualenv Python a /opt/zerto/.venv/.

Script de desplegament

# Desplegar tot
./deploy/deploy.sh

# Desplegar un component concret
./deploy/deploy.sh backend
./deploy/deploy.sh frontend
./deploy/deploy.sh observability

El script fa git pull origin main via SSH a cada VM, instal·la les dependències Python i reinicia els serveis systemd.

Configuració nginx producció

Els fitxers nginx.prod.conf i nginx.observability.conf s'instal·len manualment a /etc/nginx/sites-available/ durant la posada en marxa inicial. El deploy només actualitza els fitxers estàtics i reinicia nginx amb systemctl reload nginx.
